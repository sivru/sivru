Bugs found and fixed

CRITICAL — stdout truncated at pipe-buffer boundary (~8 KiB)

Surfaced by
QA6 — CI gate dry-run
Commit
17cd5fc — fix(cli): wait for stdout to drain before exit
Files
packages/cli/src/index.ts; regression test in packages/cli/src/commands/block.test.ts

The CLI entry called process.exit(code) immediately on main() resolution. When stdout is a pipe (rather than a TTY), process.exit terminates the process before the runtime flushes the write buffer. macOS's default pipe buffer is ~8 KiB, so any larger stdout silently truncated.

Reproducible before the fix:

$ node packages/cli/dist/index.js block extract --json packages/ | wc -c
   23603          # correct total when piped through wc
$ node -e 'JSON.parse(execSync("node packages/cli/dist/index.js block extract --json packages/", { encoding: "utf8" }))'
SyntaxError: Unterminated string in JSON at position 8178

Why this matters: the CI role-coverage gate this PR added uses execSync → JSON.parse. Without the fix, the very CI step the PR introduced would have failed on the PR itself once the JSON exceeded the pipe buffer. Any downstream MCP / pipeline / programmatic consumer of extract --json has the same exposure.

Fix:

// before
main().then((code) => process.exit(code), ...);

// after
main().then((code) => { process.exitCode = code; }, ...);

process.exitCode = code lets Node exit naturally after stdout/stderr drain; no daemon-style work holds the loop open so the process still exits immediately.

Regression test: spawns the actual built binary against a 30-block fixture and asserts execFileSync → JSON.parse succeeds. The in-process spy-based test that previously covered extract --json could not have caught this — the spy receives the data the CLI tried to write, not what survives the pipe-drain race.

MAJOR — tree-sitter grammar load race

Surfaced by
QA10 — GitHub PR CI status (visible on Node 20 all OS, Node 22 on Windows)
Commit
2ecb18a — fix(chunker): serialize tree-sitter grammar first-loads across the whole process
Files
packages/search/src/chunker/grammars.ts

The new toJSON round-trip test calls extractBlocks() on 5 different languages via Promise.all. Each first-language path hits loadGrammar() which calls web-tree-sitter's Parser.Language.load(). That call shares global WASM linker state; running it for two different .wasm files concurrently can poison the export lookup so a later read returns a function name from the WRONG grammar:

SIVRU-E1002: failed to load grammar "javascript.wasm": bad export type
for 'tree_sitter_python_external_scanner_create': undefined

Per-grammar cache prevents the SECOND call for the SAME grammar but does nothing across DIFFERENT grammars. The bug was latent in the chunker before v0.6 — no test had triggered concurrent multi-grammar first-load until the round-trip test added in this PR.

Why it only showed in CI: Node 22 on Linux/macOS happens to serialize the WASM module instantiation enough to mask the bug locally. Node 20 (newer V8 behaviour) and Windows do not. The first PR push showed 4 failed jobs (Node 20 all OS + Node 22 Windows); after the fix 2 of those 4 went green.

Fix: a process-wide grammarLoadChain Promise that serialises the first-load of each grammar. Subsequent calls hit the per-grammar cache and skip the chain entirely — steady- state path stays zero-overhead.

MAJOR — CRLF line endings silently extract 0 blocks

Surfaced by
QA9 — CRLF tolerance
Commit
548fa7f — fix: QA-surfaced edges
Files
packages/search/src/block/extract.ts; regression test in extract.test.ts

Files saved with CRLF line endings (Windows-checked-out repos) silently extracted 0 blocks. The prefix-anchored fence regex /^([ \t]*(?:\/\/\/|\/\/|\*|#)?[ \t]*)@sivru[ \t]*$/ uses [ \t]*$ with no \r tolerance, so @sivru\r\n never matched.

Reproducible before the fix:

$ # write a TS file with CRLF endings
$ python3 -c '...' > foo.ts        # content has \r\n
$ node ../dist/index.js block extract --json foo.ts
BUG: extracted 0 blocks from CRLF file

Fix: normalise CRLF→LF at the content boundary in extractBlocks:

const content = rawContent.includes("\r\n")
  ? rawContent.replace(/\r\n/g, "\n")
  : rawContent;

Tree-sitter parses CRLF input fine, but normalising once at the boundary means line ranges from the AST line up with the line array we pass to fence extraction.

Opportunities to make this better

Twelve concrete improvements surfaced by this QA pass, in roughly descending leverage order. The first three are the highest-value: they target the failure patterns that produced the four bugs found here.

O1 — /code-review should spawn the binary, not just read source

Three of the four bugs (pipe-drain, CRLF, single-file input) were invisible to the static-read code review because they live in the interaction between the code and the OS. The review correctly read all the source files but had no observation of what the binary actually does when piped, on CRLF input, or given a file. A behavioural review layer — one that exercises the artifact under several realistic invocation patterns and diffs the result against the design's stated contract — would have caught these. Worth specifying as a /code-review extension or a separate /behavior-review step.

O2 — Assertion-meaning linter for "tests that don't test"

The original threat-model test (caught by /code-review M1, fixed in eb80e84) asserted that js-yaml's library behaviour rejected hostile YAML — not that sivru's own pipeline did. This pattern is common: a test reads as "we asserted the safe outcome" but actually exercises a different code path. A small linter that flags tests where the imports in the test file don't include the production code path they claim to be testing would catch this class.

O3 — Repo-wide CRLF audit

The CRLF bug in extract.ts raises an obvious follow-up: does the chunker handle CRLF correctly? Does explain's region slicing handle CRLF correctly? Does the BM25 tokenizer? Any code path that does content.split("\n") and then matches against tree-sitter byte positions has the same potential bug class. A repo-wide grep for split("\\n") + follow-up audit is worth ~30 minutes. The fix pattern is the same: normalise at the boundary.

O4 — CLI exit-path audit for the same pipe-drain pattern

The pipe-drain CRITICAL fix replaced one process.exit(code) in packages/cli/src/index.ts. Worth grepping for process.exit across the workspace — any other CLI exit path with a large stdout payload (e.g. sivru explain --json, sivru observe static reports, sivru bench personal --json) carries the same risk. process.exitCode = code is the safer default for any CLI process; the only reason to call process.exit directly is to short-circuit a hung event loop.

O5 — Concurrent multi-grammar load test in the chunker

The tree-sitter grammar race was latent for several releases. Add a chunker integration test that Promise.alls getParser() across all 5 grammars, in a fresh-process subprocess (so the per-grammar cache doesn't mask the race). This locks in the fix and catches any future regression where someone removes the grammarLoadChain serialisation.

O6 — Fix or formally drop Windows in CI

Windows has been red on main for at least two release cycles (26240188327). The failures are real bugs in @sivru/observe (Windows short-name realpath, server bench-history fixture path assumptions). Two viable paths:

  1. Fix them — ~3 hrs work; reuses fs.realpathSync.native normalisation already in Node, fix fixture paths to be Windows-canonical.
  2. Formally drop — remove windows-latest from the matrix and document the support tier in README. Honest signal beats green-by-omission, but Windows is a real agent-runtime target so option 1 is preferable.

O7 — Stress-test the CI gate at 1000 blocks

The CI role-coverage gate's execSync has no explicit timeout (Node default is no timeout). At today's 21 blocks the output is 23 KB; at 1000 blocks it would be ~1 MB — close to the default maxBuffer of 1 MiB. Add the { maxBuffer: 64 * 1024 * 1024 } documented in deferred-item 7, and add a synthetic stress test that exercises the gate at 1000 blocks.

O8 — Use the maturity scale more deliberately

All 21 dogfood blocks were authored as maturity: stable. A more deliberate distribution would say more — the block module itself just shipped, so its three symbols (extractBlocks, validateBlock, blockToJSON) are arguably experimental until v0.7 lands and external consumers exercise the wire shape. Updating these would also dogfood the maturity scale (currently nothing in the corpus has anything other than stable, so we have zero evidence the warning paths render correctly).

O9 — Per-attack pathological fixtures

QA8 ran five YAML attack classes (anchors, __proto__, merge keys, duplicate keys, long strings) but only inline, not as committed fixtures. They should live under packages/search/src/block/__fixtures__/pathological/ so the test suite covers each attack permanently. Today's pathological/deep-nest.ts covers exactly one class.

O10 — Burn down the deferred register before v0.7 starts

Nine items sit in .auto-ship/deferred.md. Two (items 1 and 7) are real performance / correctness items that will compound with the new v0.7 surface. The remaining seven are pure cleanup (~1 hr total). Worth a single "deferred sweep" commit before DESIGN-0017 work starts — cheaper to do now while the context is fresh than once v0.7 adds its own deferred items.

O11 — Memory profile for the pathological fixture

The integration test asserts extractBlocks finishes in <200 ms on the deep-nest fixture (loose bound; the design spec is 10 ms). It does NOT assert bounded memory allocation, which the design explicitly calls for in §"Memory safety (F3)". Wiring a v8.getHeapStatistics() delta around the call and asserting it stays under ~5 MiB would lock in the F3 invariant.

O12 — Track v0.7 prerequisites surfaced by v0.6

The other (drift detector consumes SIVRU-E210 decision-no-revisit) is design-doc text only and risks being forgotten when v0.7 work starts. Worth dropping a one-line TODO into docs/design/0017-serving-authored-context.md or its task sidecar that explicitly says "drift detector adds E210 as fifth diagnostic, see DESIGN-0016 §forward-pointers".
